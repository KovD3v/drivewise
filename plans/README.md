## Recommended order and why

Run **004 first**: it is a small documentation-only task that fixes the initial
user, promise, non-goals, and private-beta pass/fail gates without blocking
engineering.

**003 next**. The maintainer selected it for execution on 2026-07-31; it remains
`TODO` until an executor actually starts. It is the largest plan, but it
unblocks everything else's visibility: today the advisor can return at most two
offers for one fictional car, so no ranked-results work can be judged. 003 does
not require a licensing decision.

**005 follows 003**. It uses 003's source-review checklist and inventory-status
tool to assess three candidate sources, then stops for explicit operator
approval before creating or importing a private pilot snapshot.

**001 can run in parallel with 004/003** because it does not depend on catalog
growth. Complete 001 before **006**; the comparison workspace deliberately
loads one immutable persisted run and also needs 003's broader result corpus.

**002 comes after the core corpus/continuity work**, because it has a blocking
input (a reviewed bollo/IPT rate table) that only the maintainer can supply.
Everything up to that input is specified.

## Dependency notes

- Plans 001–004 have no hard predecessor; Plans 005 and 006 have the
  dependencies listed below.
- **001 and 003 can run in parallel** — disjoint file sets.
- **002 must not run in parallel with 001**: both touch
  `apps/api/app/schemas/advisor.py` and `apps/api/app/repositories/advisor.py`.
  Sequence them.
- **002 Step 0 is a hard gate.** It requires a reviewed bollo/IPT rate table with
  source names, URLs, and observation dates. The plan instructs the executor to
  STOP rather than invent rates, since wrong tax figures shown to a buyer are
  worse than none.
- 003's coverage test pins `as_of` deliberately. If 003 lands and someone later
  edits fixture dates, that test's pinned time must move with them.
- **004 has no dependencies** and is documentation-only.
- **005 hard-depends on 003**. It must stop at its operator-decision gate; source
  research is not permission to rank, crawl, purchase access, or accept terms.
- **006 hard-depends on 001 and 003**. It must compare 2–3 offers from one
  immutable run and must not add backend comparison logic.

## Deferred by decision (not rejected)

These were assessed as real opportunities and consciously postponed until the
core loop closes. Recorded so they are not re-audited as new findings.

- **Price history + freshness pipeline.** No price-history table exists;
  `last_seen_at` is overwritten in place. Cheap to add now, awkward once real
  inventory accumulates. Unlocks price-drop alerts and makes the 30-day freshness
  rule meaningful. Effort M. Worth revisiting immediately after 003.
- **Re-land document evidence in red flags.** `services/advisor/document_evidence.py`
  was deleted in the working tree and `tests/test_advisor_api.py:203` now asserts
  `"document_evidence" not in first_item`. Meanwhile `model_analysis`'s
  `red_flags` are only two heuristics. The `documents` table, HNSW index, and
  embedding pipeline exist to serve this and currently serve nothing. Deferred
  because doing it properly needs a real embedding provider, which is an
  intentionally deferred dependency (`docs/architecture.md`, "Deferred Work").
  Effort L.

## Open product decisions (not plannable yet)

- **PHEV coverage.** `unsupported_phev` rejects plug-in hybrids outright
  (`scoring.py`), and EVs under 250 km WLTP are rejected for `primary_use =
  highway`. That is a meaningful slice of the Italian market rendered invisible.
  Whether this is a deliberate V1 boundary or an oversight is a product call, not
  an implementation task.
- **Which real Italian source and role may be piloted.** This remains an
  operator decision, now captured as the hard approval gate in Plan 005. The
  executor researches and recommends; it does not grant ranking permission.

## Known code-quality items outside this plan set

Surfaced in the same session's code review, tracked here so they are not lost.
Neither is a roadmap item; both are debt.

- **Eligibility rules are implemented three times** — the `WHERE` clause of
  `list_candidates`, the ~170-line `CASE` ladder in `count_excluded_candidates`
  (both `apps/api/app/repositories/advisor.py`), and `_exclusion_reason` in
  `apps/api/app/services/advisor/scoring.py`. Two languages, 27 reasons kept in
  sync by hand, and the SQL half only runs under `TEST_DATABASE_URL`. Minor drift
  already exists: Python's `_integer` rejects negative mileage as
  `missing_mileage`, the SQL only checks `IS NULL`. **Do not attempt this while
  003 is in flight** — 003's whole safety property is that eligibility rules stay
  frozen.
- **Italian copy is inconsistently accented.** `Advisor.tsx` renders `Citta`,
  `__root.tsx` renders `o e stata spostata`, and `scoring.py`'s user-facing
  rationale strings contain `e contenuto` / `versatilita` / `e elevato`, while
  `ModelAnalysis.tsx` correctly uses `è` / `più` / `affidabilità`. Also
  `Home.tsx` is still in English while every other page is Italian. Small, fully
  specified, no dependencies.

  duplicating what FastAPI already serves at `/openapi.json`, so it will rot —
  but it also documents scoring semantics and exclusion reasons that OpenAPI
  cannot express. Not worth a plan until someone is actually misled by it;
  trimming it to the non-generatable parts is a 20-minute editorial task, not an
  engineering project.

  `apps/web/src/api/drivewise.ts` is 977 lines, most of it a second
  implementation of backend search scoring and model-analysis verdict logic
  (`:664-751`). Real, but the path is off by default (`VITE_USE_MOCK_API`), so it
  is latent rather than active risk. Revisit if the mock ever diverges visibly.
